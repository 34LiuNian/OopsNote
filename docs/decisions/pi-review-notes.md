# 对 Codex 评估的修正意见

> 用于指导 Codex 后续工作

---

## 1. 关于视觉问题

**Codex 说：** DeepSeek 不支持图片，需要额外写 Qwen Extension。

**修正：** 不需要。pi 的架构允许在工具层面调用不同模型，主 DeepSeek 不动：

- 写一个 `ocr_image` Extension 工具（约 20 行代码）
- 内部调用 Qwen-VL API（DashScope）
- DeepSeek 遇到图片时调这个工具就行

不需要换主模型，不需要额外部署服务。

---

## 2. 关于双后端策略

**Codex 说：** 做双后端（PiRpcBackend + HermesBackend），保留 Hermes 回退。

**修正：** 可以做但要有明确时限：

```
Phase 1 — PoC（2-3 天）
  └── Pi RPC 跑通一条流水线

Phase 2 — 双后端并行（1 周）
  ├── Web 默认走 Pi
  └── Hermes 保留为 fallback 开关

Phase 3 — Hermes 下线
  └── 彻底移除 Hermes
```

不要无限期保留双后端，增加维护成本。

---

## 3. 关于工期评估

**Codex 说：** PoC 约 2-3 个开发日。

**修正：**

- **PoC**（跑通一条流水线）：2-3 天 ✓
- **生产级**（错误恢复、超时、重试、成本追踪、双后端切换）：5-7 天
- 第一版做 PoC 验证可行性就够了

---

## 4. 关于子 Agent 并行

**Codex 说：** 第一版不建议过度并行，流水线仍有依赖关系。

**同意。** 具体来说：

```
OCR → solve → verify → tag → finalize
                   ↑
             知识打标可以和解题并行，
             但错误归因依赖解题结果
```

相关性高的并行有意义（如知识打标与解题），盲目并行只会增加成本和复杂度。

---

## 5. 关于 pi 的配置模型

**Codex 可能不知道的这些点：**

| 特性 | 说明 |
|------|------|
| 项目级 `.pi/` 配置 | 可提交 Git，clone 即用 |
| 天然多开 | 每个实例独立进程，无锁 |
| RPC 模式 | `--mode rpc` 原生支持 abort、事件流、token/cost 统计 |
| `--no-builtin-tools` | 可以只加载自定义工具，没有任何多余负担 |

---

## 总结

Codex 的大方向是对的（Pi 比 Hermes 更合适），但细节上有几处需要调整：

1. **视觉** → Extension 工具，不需要额外部署
2. **双后端** → 可以但要有时限
3. **工期** → PoC 2-3 天，生产 5-7 天
4. **配置** → `.pi/` 目录随项目走，无需额外配置管理
